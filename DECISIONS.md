# Decisions

Architecture and scope decisions, in the order they were made. Two lines each: what, why.

## Checkpoint 1

**Contract sharing pattern**: oRPC router is defined directly in `packages/contracts` (procedures + handlers together), not split into a separate contract-first layer. `apps/web` imports the router's type only (`import type`), so server code never reaches the frontend bundle — simplest path to full type safety, mirrors tRPC's ergonomics.

**Docker Compose scope**: only Postgres runs in Docker locally; `apps/server` and `apps/web` run natively via `bun run dev`. Matches how Railway will run them as three separate native services, so no Dockerfiles are needed until deploy.

**Typecheck strategy**: per-package `tsconfig.json`s use TS project references (`composite: true`), so a single root `tsc -b` incrementally typechecks every workspace and catches cross-package breaks.

**`TrainingPlan.config` / `PlannedWorkout.prescription` as `Json`, not `String`**: keeps the schema flexible while the plan-generation module's exact shape is still being designed (Checkpoint 3+), avoiding a migration when it settles.

**`PlannedWorkout.day` and `*.type` fields as Prisma enums, not free strings**: compile-time safety for the plan-generation logic. Actual calendar date is derived from `startDate + week + day`, never stored directly.

**Unit test runner: `bun test`, no Vitest**: the stack is already Bun-native; avoids an extra dependency for behavior Bun already provides.

## Checkpoint 2

**GitHub repo made public**: GitHub Free doesn't allow required status checks (branch protection or rulesets) on private repos. Confirmed with the user; also reasonable for a work sample meant to be shared with an interviewer.

**CI runs `bun run check` only, no DB service**: `tsc`/`eslint`/`knip` never touch Postgres. DB-backed tests (Checkpoint 4) will use Testcontainers, which spin up their own ephemeral Postgres rather than a shared CI service container.

**Prisma client generation moved to a `postinstall` hook** (`packages/db/package.json`): CI does a from-scratch `bun install` with no prior `migrate dev` step, so `@prisma/client`'s types silently fell back to `any` until generated — caught by CI failing on `packages/db/src/client.ts`, not locally, since local `node_modules` already had a generated client from Checkpoint 1.

**Auth transport: Bearer token, not cookies**: the web and server will live on different Railway domains, so a header-based token (via Clerk's `getToken()`, bridged into the oRPC client's `headers` callback) avoids cross-origin cookie/`credentials` complexity entirely.

**Reusable `protectedProcedure` middleware** (`packages/contracts/src/procedures.ts`) over ad hoc per-procedure auth checks: uses oRPC's `os.$context<AppContext>()` + `.use()` to throw `UNAUTHORIZED` once, centrally, so Checkpoint 3's real procedures (`createPlan`, `logSession`) just extend `protectedProcedure` instead of re-checking `context.auth` everywhere.

**`me` procedure returns only the Clerk `userId`, no DB lookup**: syncing Clerk users into the `User` table (get-or-create by `clerkId`) happens naturally in Checkpoint 3 when `createPlan` first needs a real `userId` FK — doing it now would be speculative.

**`react-router-dom` for client-side routing**: introduced now because a public `/` vs. protected `/dashboard` split needs distinct URLs, and Checkpoint 3 adds more pages regardless.

**`db:deploy` script instead of `bunx prisma migrate deploy`**: `bunx prisma` from the repo root fetched a fresh latest Prisma (v7, breaking schema-format change) rather than the workspace's pinned v6 devDependency. `bun run --filter '@firstloop/db' db:deploy` resolves the local pinned binary correctly.

**Prisma migration runs at server *start*, not Railway's build step**: Railway's build containers can't reach `*.railway.internal` hostnames — that private network is only available to running/deployed services. `prisma migrate deploy` is chained into the server's start command instead; it's idempotent (no-ops with no pending migrations), so this is safe on every deploy.

**Server listens on `PORT` (Railway's convention) falling back to `SERVER_PORT`**: added `PORT` as an optional env var that wins when present; `SERVER_PORT` stays the local-only default so it doesn't collide with tooling that injects its own `PORT` for local preview.

## Checkpoint 3

**Persistent nav shell (`AppShell`) added ahead of schedule**: discussed with the user before building — a public `/` vs. protected pages already needed structure, and future sections (nutrition, strength tracking) the user wants to add later get a slot to land in without a nav restructure. Cheap now, disruptive later.

**`packages/plan-engine` has zero dependencies, not even on `@firstloop/db`**: originally imported Prisma's `DayOfWeek`/`WorkoutType` enums for convenience. Adding the seed script (which needs both Prisma writes and `generatePlan()`) would have made that a circular workspace dependency (`db → plan-engine → db`). Fixed by having plan-engine define its own string-literal-union types that mirror the Prisma enums by value — genuinely standalone now, matching what "swappable module" was supposed to mean in the first place.

**One active plan per user, most-recent-wins**: `getDashboard`/`createPlan` don't do multi-plan selection UI. `TrainingPlan` is still one-to-many from `User` in the schema, so old plans aren't lost — just not surfaced yet. Simplest thing that works for a single-plan-at-a-time product today.

**Plan `startDate` truncated to midnight UTC at creation**: found via manual testing — `new Date()` (with time-of-day) as `startDate` combined with midnight-aligned session-log dates (from a plain `<input type="date">`) meant a session logged on a plan's creation day could fall *before* that plan's own week boundary and silently vanish from "this week." Both now align to day boundaries.

**Seed script hardcodes the demo user's email instead of calling Clerk's API**: avoids `packages/db` needing `@clerk/express`/`CLERK_SECRET_KEY` just to run a one-off script — the real `getOrCreateUser` path (used by every actual request) still fetches the authoritative email from Clerk on first real login.

## Checkpoint 4

**`packages/contracts` gets an explicit `exports` map with a `./schemas/*` subpath**: the intake form needed a real (value, not type) import of `createPlanInputSchema` for client-side validation. Importing anything through the main barrel (`@firstloop/contracts`) risks pulling in `router.ts` — which imports `@firstloop/db`, and `db`'s `client.ts` instantiates a real `PrismaClient()` at module scope. Whether a bundler tree-shakes that away is not something to gamble on for "does server code end up in the browser." The `./schemas/*` subpath resolves straight to a schema file, never touching `router.ts`. Verified by grepping the built client bundle for Prisma/Clerk-backend strings (zero matches).

**`packages/contracts`'s schemas no longer import Prisma enum values from `@firstloop/db`**: `session.ts`/`dashboard.ts` used `z.nativeEnum(WorkoutType)` from `@firstloop/db` — same PrismaClient-instantiation risk as above, since importing the enum meant loading `db`'s `client.ts` module. Replaced with local `z.enum([...])` schemas (`schemas/enums.ts`) mirroring the same values, same pattern already established for `packages/plan-engine`.

## Checkpoint 6

**Light is the primary, designed identity — not dark**: the app has no dark-mode toggle today and light is what a reviewer actually sees; dark tokens still extend the existing `.dark` scaffold via `prefers-color-scheme` for completeness, but weren't the design's starting point. Register: an instrument panel / GPS watch face, not a wellness app, for a persona (lifter + cyclist + first-time marathoner) who already lives inside training data.

**Signature element is a phase-arc, computed client-side, Dashboard-only**: `apps/web` now depends on `@firstloop/plan-engine` directly (previously server-only) to call `computePhaseBoundaries` — a pure, zero-dependency function — so the arc reflects each plan's actual base/build/peak/taper proportions instead of a hardcoded shape. No new data fetching; it lives only on Dashboard, not the nav shell, so `AppShell` stays presentational and doesn't need its own query.

**Three type roles (Big Shoulders Display / IBM Plex Sans / IBM Plex Mono), loaded via Google Fonts `<link>`**: deliberately not Inter or Space Grotesk. Numbers — mileage, pace, duration, RPE, dates — get their own monospaced, tabular register everywhere, distinct from prose; this was judged the single highest-leverage typographic decision for an app whose users already read a watch face all day.

**Log-a-run form got the token/type/layout system but not a full ShadCN rebuild**: full validation + component rebuild for that form is explicit Checkpoint 7 scope (closes issue #12). Checkpoint 6 restyled it in place (colors, type, focus states, Card wrapper) so it's visually consistent with everything else in the meantime, without front-running the next checkpoint's work.

## Checkpoint 7

**Session history is a real `/history` page, not just a polished weekly list**: the brief's "session history view" was ambiguous between styling the existing "Logged this week" list and building actual multi-week browsing. Asked the user directly — they chose the full page. New `getSessionHistory` procedure returns all of a user's session logs, most recent first, no pagination (data volume for one runner's training cycle doesn't need it). This meaningfully overlaps with issue #11 (dashboard only shows the current week) but doesn't close it — #11 is also about browsing *planned* past/future weeks, which this doesn't touch, so it's left open with a progress comment instead of closed.

**Dashboard's weekly mileage chart extends `getDashboard` instead of adding a new procedure**: planned-vs-actual turned out to be a clean lift — `prescription.distanceMiles` already exists per planned workout, and the data's one query away from what Dashboard already fetches on mount. Returns the full `1..totalWeeks` array (not just weeks-so-far) so the chart shows the whole planned arc with actuals filling in as weeks pass, consistent with how PhaseArc already shows the whole plan's shape rather than just "so far."

**New test types (Testcontainers, Playwright) stay out of `bun run check`, but are still CI-required**: both add real external dependencies — Testcontainers needs Docker, Playwright needs the whole app running — that would slow down every local check. Added as separate `test:integration`/`test:e2e` scripts and separate `integration`/`e2e` CI jobs alongside `check`, all three required in branch protection. `bun run check` keeps doing exactly what it did before.

**Testcontainers integration test uses dynamic imports, not static ones**: `@firstloop/db`'s Prisma client is a module-scope singleton built from `DATABASE_URL` at import time. Since Testcontainers only knows the container's port after it starts, the test starts the container first, sets `DATABASE_URL`, *then* dynamically `import()`s `@firstloop/db`/`@firstloop/contracts` so the singleton picks up the right connection string. Also mocks `@clerk/express`'s `clerkClient.users.getUser` via `bun:test`'s `mock.module`, so `getOrCreateUser`'s create path is exercised for real without the test suite depending on live Clerk network calls — same principle already planned for Checkpoint 9's AI Coach mock.

**Playwright's e2e test lives in a root-level `e2e/` directory with its own `tsconfig.json`, not nested under `apps/web`**: it exercises the whole integrated system (server + web + Postgres + Clerk), not one package, so it doesn't belong to any single workspace. The dedicated `e2e/tsconfig.json` (and moving `playwright.config.ts` into `e2e/`) was also a practical fix — Playwright's own TS loader couldn't resolve the root `tsconfig.json`'s solution-style project references the way `tsc -b` does, and choked trying. Auth uses `@clerk/testing`'s official Playwright helpers (ticket-based sign-in by email against the existing dev Clerk instance) rather than driving the interactive sign-in modal.

**Playwright test asserts on a per-run-unique duration value, not notes text**: first attempt used a unique marker string in the session's `notes` field, but neither Dashboard nor History render `notes` at all, so the assertion could never find it. Switched to a duration value derived from `Date.now()`, which *is* rendered — and made it unique per run (not a fixed constant) after discovering a fixed value collided with itself on a second local run against the same persistent dev database, since Playwright's `webServer` reuses whatever's already running locally rather than a fresh DB per run like CI gets.

## Checkpoint 8

**Attempted a pre-prod/prod split, reverted it — staying on a single Railway environment**: built out the repo/CI side (a `prod` branch, matching branch protection, a CI push trigger, Railway-Environments-vs-Clerk-instance-split decisions logged and later refined) before discovering Railway requires a paid plan to run a second environment. Decided against paying for a second environment purely to demonstrate the pattern on a take-home project — the cost isn't justified by what it'd prove here. Reverted the `prod` branch, its branch protection, and the CI trigger change; this project deploys to the one Railway environment that's been live since Checkpoint 3, tracking `main`, and stays that way going forward. A real, plain engineering tradeoff: infrastructure cost vs. a nice-to-have pattern that doesn't change what the project demonstrates.

## Checkpoint 9

**Strength scheduling lives in its own zero-dependency package, `packages/strength-engine`, not folded into `plan-engine`**: mirrors `plan-engine`'s exact design (pure functions, no DB, program defined as swappable data) for the same reason — a future different program is a data change, not a rewrite. It doesn't import `plan-engine`'s types either; the scheduler takes a plain `WeekContext` shape, so it stays a genuinely generic "place a program's sessions around fixed days" capability, not code specific to Glute Gladiator.

**"Down/deload week" maps to the running plan's existing `taper` phase**: discussed with the user before building. Plan-engine has no periodic within-block cutback-week concept (mileage grows monotonically through base/build, holds at peak, then tapers) — adding one would touch working, already-tested running-plan behavior just to serve strength scheduling. Taper is a real, already-computed reduced-load signal, so the scheduler keys off that instead.

**Strength sessions claim REST-day placeholders, never RUN or BIKE days**: `generatePlan` already fills every day of the week (RUN, then BIKE, then REST catches whatever's left) — removing the old naive `liftDaysPerWeek`-driven LIFT block just means REST fills those days instead. The orchestration in `createPlan` treats each week's REST rows as the scheduler's available slots and drops any REST row the scheduler actually claims before persisting, so RUN/BIKE days are never touched.

**`liftDaysPerWeek` removed from `PlanIntake`/the intake form entirely**: once a real program dictates its own weekly session count and structure, a user-chosen lift-day count doesn't mean anything anymore — same reasoning the app already applies to running (nobody picks "how many quality-run days," that's derived from phase). Every generated plan now includes the strength program automatically.

**Found via verification, not by inspection: the interference rule was silently dropping Lower A for the entire peak phase.** Spot-checking seeded data (not just unit tests) showed weeks 31–36 scheduling only 2 of the reduced 3 sessions, every single week — Upper A and Upper B, never Lower A. Root cause: this plan's specific day layout (quality runs Wed/Fri, long run Sun) leaves only Tue/Thu/Sat open during peak weeks, and all three sit immediately before a run day, so the interference rule (never place a lower session the day before a quality/long run) had no legal day to place Lower A on at all — and the scheduler's original fallback logic just dropped the session rather than degrade the rule. Fixed by adding a third fallback tier: prefer full spacing, then prefer any interference-respecting day, and only as a last resort place on the least-bad day regardless of interference — because the source program's own peak-week rule explicitly keeps Lower A in the reduced set, so silently disappearing it for six straight weeks was further from the doc's intent than the fallback is. Added a regression test for this exact scenario. This is the kind of gap that unit tests alone (synthetic, individually-reasonable week contexts) don't catch — it only showed up once real data was eyeballed across a full plan.

**Two exercises share "(block reps)" in the source doc, only one is the session's "primary" lift**: Lower A lists both Barbell Hip Thrust (explicitly "the primary progression lift") and Barbell RDL as `(block reps)`, but only Hip Thrust's notes call it primary. Modeled both as `usesBlockReps: true` (their reps resolve from the block's `mainLiftReps` at generation time) while reserving `isMainLift` for the one exercise per session the doc explicitly names — a literal reading of what's actually in the table rather than assuming "block reps" and "primary lift" are the same thing.

**Session drop order beyond the documented 4→3 cut is inferred, not specified**: the doc explicitly says Lower B drops first when cutting to 3 sessions during peak weeks, but says nothing about a deeper cut. `sessionDropOrder` in the program data continues past that point as a reasonable fallback (kept in code as an explicit "not a documented rule" comment) rather than leaving the scheduler with no defined behavior if it's ever needed.

## Post-Checkpoint-9 fix: three strength modes on intake

**`SessionTemplate.isLowerBody` split into `respectsInterference` + `spacingGroup`**: product review asked for a "custom" strength mode that respects the interference rule (no session the day before a quality/long run) but explicitly skips the 48-hour lower-body spacing rule, since we don't know which of a user's own sessions are lower-body-heavy. One boolean couldn't express "needs interference avoidance but not spacing" — Glute Gladiator happened to need both together for the same sessions, which is what let `isLowerBody` get away with doing two jobs at once. Decoupled them properly (spacing keyed by an optional group name, multiple sessions can share a group via `Map<string, number[]>`) rather than a same-boolean workaround, so "feed the same generic scheduler a minimal synthetic program" is actually true, not just true for Glute Gladiator. `SessionName` also widened from a literal union naming Glute Gladiator's four sessions to a plain `string` — a "generic" scheduler hardcoding one program's session names in its type was already a smell, custom mode just made it obviously wrong.

**Custom mode is a data trick, not a second scheduler**: `buildCustomProgram(n)` produces N sessions with `respectsInterference: true`, no `spacingGroup` (so the existing spacing check is trivially always-satisfied — nothing to compare against), `exercises: []`, and a 1-week cycle with no real block progression. Fed through the exact same `scheduleStrengthSessions` Checkpoint 9 built. No peak-mileage cutback (`fullSessionCount === reducedSessionCount`), matching how `bikeDaysPerWeek` already behaves — bike doesn't reduce during peak weeks either, so custom lifting shouldn't either.

**Verified, not assumed: Dashboard already showed real session names/exercise counts, not generic "Lift" placeholders** — this was built correctly in Checkpoint 9 and confirmed again here by reading the code before claiming it either way. What building custom mode *did* surface: `describePrescription`'s exercises check was truthy for an empty array (would've shown "Lift session · 0 exercises," reading like a bug even though it's real data), and `LogSession`'s initial `type` field was derived from whether the linked prescription had exercises rather than the actual workout type — a custom lift session (no exercises) would have silently defaulted the form to "Run." Both fixed; both would only have shown up once custom mode existed to exercise them.

## Checkpoint 11

**Generic day-placement logic extracted into a new zero-dependency package, `packages/scheduling`**: the running-frequency fix needed the exact same "place a set of named slots into a week, respecting interference and same-group spacing" capability the strength scheduler already had (`placeSessions`/`isBlockedByInterference` in `strength-engine/src/schedule.ts`) — those functions never touched anything strength-specific, only `.name`/`.respectsInterference`/`.spacingGroup`. Rather than duplicate that logic a third time or have one domain package depend on the other, pulled `Slot`/`placeSlots`/`DayOfWeek`/`WEEK_DAY_ORDER` into `packages/scheduling`, which `plan-engine` and `strength-engine` both now depend on. `plan-engine` goes from zero dependencies to one, but `scheduling` is itself pure day-of-week math — nothing DB/Clerk-shaped — so it doesn't undermine the reason `plan-engine` stayed standalone in the first place (Checkpoint 3).

**Feasibility minimums (20 weeks for a first marathon, 12 for a repeat one) are a stated coaching judgment call, not a formula**: there's no principled way to compute "enough runway" from first principles here — these are commonly-cited, conservative minimums for an injury-conscious build from a modest base. Logged plainly as judgment calls (in code comments and here) rather than presented as more rigorous than they are, per explicit instruction. The check never hard-blocks plan creation; it only names the gap.

**Feasibility warning is computed once at plan creation and persisted in `TrainingPlan.config`, not recomputed live on every dashboard load**: mirrors the existing `strengthMode`/`customLiftDaysPerWeek` pattern already stored there. `getDashboard` reads it back out and returns it so it stays visible as a persistent banner rather than a one-time toast. Noticed in passing that the *existing* injury-flag warnings from `generatePlan` have the same one-time-only gap (returned in `createPlan`'s response, never persisted or re-shown) — left that alone since fixing it wasn't in scope for this checkpoint, but it's now a known, named gap rather than an unnoticed one.

**Quality-run slots get a `spacingGroup` even though only interference-avoidance was explicitly requested**: without some minimum spacing between two quality-run days, a peak-phase week could land tempo and intervals on adjacent days — worse than the old hardcoded Wednesday/Friday, which were always exactly 2 days apart. Reused the same `spacingGroup` mechanism `placeSlots` already provides (the exact thing built for lower-body spacing in Checkpoint 9) rather than inventing a second constraint system, and kept the 2-day minimum as a floor that preserves the old fixed placement's spacing without hardcoding the days themselves.

**Easy-run duration is a flat 30 minutes, not derived from mileage**: matches how quality runs already work in this codebase (flat 40/45 minutes, not mileage-derived either) — consistent with the existing model's level of precision rather than introducing a new one just for easy runs.

**Running progress buckets by calendar week (Monday-start, UTC) across a user's entire logged history, not by plan week**: "over the logged history" reads as everything a runner has logged, and a runner's history can span more than one plan (the app already allows creating a new plan; old `PlannedWorkout`/`SessionLog` rows aren't deleted). Average pace per week is mileage-weighted (total logged minutes ÷ total logged miles for runs with both fields) rather than an average of each run's individual pace, so one very short run doesn't skew a week's number as much as it would in a naive average.

## Checkpoint 12 — Full plan view

**Renamed the existing `/intake` nav link from "Plan" to "Goal"**: this checkpoint's whole point is a page that actually shows the plan, so giving that the "Plan" label meant the existing intake link (which sets your race goal, not a plan view) needed to stop using it — two nav items both called "Plan" pointing at different pages would have been confusing on day one, not a hypothetical problem to fix later.

**Layout is tabs by phase, accordion by week within a tab — decided against the real 16/14/6/3 week split, not chosen up front**: a flat 39-week accordion is too long to scan, and week-level tabs (no phase grouping) don't read as an arc. Tabs give a 4-click-max "jump to any point in the plan" structure that mirrors how `PhaseArc` already segments the plan visually; each phase's own week count, even base's 16, is fine as one-line collapsed accordion rows. The current week's accordion item opens by default and gets the same `--flare` treatment `PhaseArc`'s current-week marker already uses, so both "you are here" signals share one color language instead of inventing a second one.

**New `getPlanOverview` procedure shares a `computePlanMeta` helper with `getDashboard`, rather than duplicating the totalWeeks/currentWeek/phase/feasibilityWarning computation a second time**: both procedures need the exact same derived fields from a plan row; pulled that into one function in `router.ts`. Behavior-preserving for `getDashboard` — confirmed by its existing integration-test assertions still passing unchanged. Also extracted `describePrescription` (previously local to `Dashboard.tsx`) into `apps/web/src/lib/prescription.ts` so the new Plan page renders workout rows with identical formatting instead of a second copy that could drift from the original.

**Full plan view stays fully read-only — no "Log this" action on any row, even though Dashboard's current-week list has one**: the checkpoint explicitly scoped this to read-only, same standing as the already-tracked editing/rescheduling issue (#10). Omitting the action entirely (rather than, say, disabling it) keeps the page's purpose unambiguous — it's for seeing the arc, not for logging against it.

**Observed via this view, not fixed by it: peak-phase weeks sometimes place fewer strength sessions than the program's own "reduced count" of 3.** Browsing every week surfaced that once running (Checkpoint 11) claims 4 days in a peak week (long run + 2 quality + 1 easy) and bike claims 1 more, only 2 days are left for strength — one short of the 3 the program's peak-cutback rule targets. This is the same honest, pre-existing truncation behavior already documented for `bikeDaysPerWeek` and custom strength mode ("if a week's available days can't fit every session, fewer get placed") — not a new bug, and not something a read-only view is the right place to fix. Worth naming here as a real interaction between two separate checkpoints (11's higher running frequency, 9's strength scheduler) that only became visible once the whole plan could be browsed at once, exactly the kind of gap this checkpoint's own verification loop is supposed to surface.

## Checkpoint 13 — Safety and correctness remediation

Prompted by a coach-persona and designer-persona review of the actual generated output (not the code in the abstract) — both reviews are recorded in full in this session's transcript. Four real problems came out of it; this checkpoint fixes them and only them. The review's other findings (no cutback weeks in base/build, the fixed 19mi peak long-run distance regardless of experience or current mileage, static block-level strength progression with no double progression, Custom mode's missing explanatory caption, interference rules being invisible in the UI) are explicitly *not* addressed here — they're documented as known limitations in the Checkpoint 14 write-up instead of silently dropped.

**`intensityRank` is a new axis on `BlockDefinition`, deliberately decoupled from the existing `isDeload` boolean.** Glute Gladiator's "Test/Deload" week is `isDeload: true` (a volume-reduction week by the program's own accounting) but its actual prescription is "work to a heavy top set on hip thrust, squat, RDL, bench, row" — near-maximal effort, not a light week. Capping peak-mileage running weeks by `isDeload` alone would have let that week through unmodified, since it already reads as "deload." `intensityRank` (Deload=0, Build=1, Strengthen=2, Peak=3, Test/Deload=4) measures actual load instead, and a new `isPeakMileageCap` flag designates Strengthen as the block a peak-mileage week steps down to when the raw cycle position would land on something above it. Verified against the app's own seeded 39-week demo plan: weeks 33-35 (raw "Peak") and week 36 (raw "Test/Deload", the near-1RM testing week that was landing on the single highest-fatigue week of the whole plan) now both resolve to "Strengthen."

**`checkDayEconomy` warns about two distinct failure modes — understaffed weeks and unsafe spacing — with no minimum-affected-week threshold before it speaks up.** A week counts as understaffed if fewer sessions got placed than the program intended (session count, not exercise-level), and as unsafe-spacing if two sessions sharing a `spacingGroup` land closer together than `minDaysBetweenGroupedSessions`. Even a single affected week triggers a warning, worded proportionally ("2 of 39 weeks" vs. "39 of 39 weeks") rather than suppressed as noise — the whole point was "don't silently degrade," so a real gap that only shows up once still gets named. Computed once at `createPlan` (and in the seed script, mirroring `feasibilityWarning`'s existing pattern) and persisted in `TrainingPlan.config`, not recomputed live. Reseeding the demo persona (4 running days + 1 bike day + program mode — the app's own defaults) now produces a real, honest warning: 39 of 39 weeks understaffed, 33 of 39 with Lower A/Lower B back-to-back. Deliberately did not change the demo's chosen inputs to dodge this — a visible warning on the seeded plan is the proof the fix works, not a bug to hide before submission.

**Checked `docs/strength-program.md`'s actual "Swap Table" before building anything against it — it's titled "(Equipment or Preference)" and is genuinely not injury-oriented.** Of its five entries, exactly one is defensible for a knee flag: "Back Squat → Front Squat, Hack Squat, or Leg Press," and of those three, only Leg Press (fixed path, less stabilization demand) is actually easier on the knee — Front/Hack Squat aren't, and I'm not claiming otherwise just because they're in the same table row. The other two knee-loading movements in the program, Bulgarian Split Squat and Walking Lunge, have no documented alternative anywhere in the source doc, and Glute Gladiator is explicitly the literal, verbatim source of truth per Checkpoint 9's own constraint — inventing replacement exercises that aren't in it isn't on the table. Those two get dropped from the session for a flagged knee instead, which is the honest version of "no defensible substitute exists" rather than a fabricated one. For "IT band," "Shin splints," and free-text "Other" flags: no exercise-level change at all — nothing in the doc or in defensible general judgment gives a groundable substitution the way the swap table does for knee, and saying plainly that nothing was adapted beats pretending a change happened. This is stated outright in the persisted injury note rather than left to silence.

**The persisted injury note is new, separate router-level logic, not an extension of `plan-engine`'s existing transient `warnings` array.** `generatePlan`'s per-flag messages (unchanged, still returned once from `createPlan`) don't know anything about strength — they're running-only. The new `injuryWarning`, stored in `TrainingPlan.config` and read back by the same `computePlanMeta` helper `feasibilityWarning`/`strengthWarning` already use, is a router-level concern precisely because it's cross-cutting (it names both the running mileage reduction and the strength-side adaptation status in one sentence). It reuses plan-engine's own already-worded running sentences rather than reconstructing the reduction percentage independently, so the two can't drift out of sync.

**Home page's ping health-check box removed outright, nothing put in its place.** It was Checkpoint 1 scaffolding that got restyled into the Checkpoint 6 card treatment in passing but never actually removed — the backend `ping` procedure itself stays (a legitimate lightweight health check), just no longer surfaced as UI.

**Noted in passing, not fixed here: `SessionLog` rows survive a plan's deletion during reseeding (`onDelete: SetNull`, not `Cascade`), so every past `bun run --filter '@firstloop/db' db:seed` has left behind orphaned freeform logs from whichever plan existed at the time.** Spotted several with implausible multi-thousand-minute durations while spot-checking the reseeded demo plan for this checkpoint — pre-existing seed-script data hygiene, unrelated to any of today's changes, and out of this checkpoint's explicit scope. Worth a cleanup pass before the final submission push in Checkpoint 15.

## Checkpoint 14 — Stretch features (nutrition, AI coach)

**Both stretch features got built, nutrition first, on the checkpoint's own priority ordering.** Nutrition was the cheaper of the two and was finished before the coach was started, so a blowup on the API integration couldn't have cost both features. Explicitly out of scope and still future work, unchanged from the checkpoint brief: a tool-using coach, an agentic CI review step, Terraform.

**The nutrition page is static content with no state, no input, and no calculator — the ranges are hardcoded and deliberately coarse.** A per-runner carb target would need bodyweight, sweat rate, GI tolerance, and race pace, none of which the app collects and none of which it should start collecting for a reference page. Coarse published ranges by long-run duration are the honest version of what this page can actually know; a narrower number would imply a precision the feature isn't doing the work to earn. The page says outright that nothing on it is personalized and points at a professional for individual advice, rather than letting placement inside a training app imply otherwise.

**The AI coach comments on training; it is not what makes training safe.** `plan-engine` and `strength-engine` already enforce progression, taper, peak-week intensity caps, spacing, and injury adaptation at generation time — all of it deterministic and unit-tested. The coach reads the last two weeks and says how it went. This split is why the endpoint is allowed to fail: an outage costs a paragraph of commentary, not the correctness of anyone's schedule. Nothing in the system prompt asks the model to modify the plan, and it's told not to.

**No API key is a first-class supported state, not an error.** `createAnthropicCompletion` returns `null` when `ANTHROPIC_API_KEY` is unset and the endpoint returns `status: "unavailable"` before doing any database work — so a fresh clone, CI, and a local dev environment all run the whole app with no key and no failures. Any exception from the live call is caught and collapses to the same state, because a coach outage must not take the dashboard down with it. `ANTHROPIC_API_KEY` is documented as optional in `.env.example` for exactly this reason.

**The Anthropic call sits behind a `CoachCompletion` function type, which is the seam the tests substitute.** Everything above it — the 14-day window math, adherence counting, missed-session detection, mileage bucketing, prompt assembly, response parsing — is pure and unit-tested with no network and no key (`packages/contracts/src/lib/coach.test.ts`, in the fast `bun test` path). The SDK is `import()`ed lazily inside the completion, only once a key exists. CI therefore needs no key and incurs no cost, per the checkpoint's explicit constraint.

**Structured output via `output_config.format` with a raw JSON Schema, parsed and then re-validated with Zod.** The schema constrains the model to `{guidance, concern}` with `concern` nullable, so "nothing to flag" is a representable answer rather than something the model has to phrase its way out of — the prompt tells it not to manufacture a concern, and the schema gives it somewhere to put that. The response is still `JSON.parse`d and run through a Zod schema on the way out; a malformed response fails loudly into the caught path instead of rendering as guidance. Used the raw JSON Schema rather than the SDK's Zod helper to avoid coupling the contract to a specific Zod major version.

**The coach is button-triggered on the dashboard, not fetched with the rest of the page.** It is the only call in the app that costs money per invocation, so asking for it is an explicit act. Fetching it automatically on every dashboard load would bill a request for every navigation, including ones where nobody reads it.

**The seed script now deliberately leaves the most recent past long run unlogged.** It previously relied on a 12% random skip, which meant a demo could easily land on a persona with perfect adherence and a coach with nothing to say. Choosing the miss explicitly — and logging which date it chose — makes the demo reproducible and gives the concern path something real to find, which is what the checkpoint asked for.

**Re-ran the Checkpoint 4 bundle-leak check after adding `@anthropic-ai/sdk` to `packages/contracts`, because that's exactly the shape of dependency that caused the original problem.** Built the web client and grepped the output: zero occurrences of `PrismaClient`, `prisma`, `@anthropic-ai`, `anthropic`, or `api.anthropic.com`. The one `ANTHROPIC_API_KEY` hit is the literal string in the coach card's "not configured" copy, not a value or an import. The `./schemas/*` subpath rule that made this safe the first time is what keeps it safe now — the web app value-imports the new coach schema through `@firstloop/contracts/schemas/coach`, never through the root barrel.

**"No key configured" and "the call failed" are separate states, split after the first one misled a real debugging session.** Both originally collapsed to `status: "unavailable"`, so a correctly-configured key whose account had no credit rendered as "The coach isn't configured in this environment. Set ANTHROPIC_API_KEY…" — the single most misleading thing to show someone who had just set `ANTHROPIC_API_KEY` correctly. They're now distinct: `unavailable` means no key (fix is a config change), `failed` means a key exists but the call didn't succeed — bad key, exhausted credit, upstream outage, malformed response — and points at the server log, which already carried the real reason. The cost of conflating them isn't theoretical; it sent the first person to configure this feature looking in exactly the wrong place.

**Added `e2e/stretch-features.spec.ts` rather than verifying by hand.** The coach assertion is written key-agnostically: it checks the request *settles* (the button returns to an enabled "Ask again" and the loading state clears) rather than asserting on guidance text, so the same test passes with or without a key configured and never depends on model output being stable. That also pins the real requirement — a coach outage must never leave the dashboard stuck loading.

## Checkpoint 15 — Systems diagram and write-up

**Not logged when it happened, recorded here: the orphaned-`SessionLog` cleanup shipped in commit `2301045` during Checkpoint 14, but no decision entry was ever written for it.** Checkpoint 13 flagged it as "worth a cleanup pass before the final submission push" (above) and then the fix landed as a bug fix without the log catching up — the exact drift the decisions log exists to prevent. The substance: `SessionLog.plannedWorkoutId` is `onDelete: SetNull`, so deleting the previous plan on reseed orphaned its logs instead of removing them, and mileage is queried by user (correctly — a runner's history legitimately spans plans), so every past reseed stacked another full history on top of the last. 450 orphans inflating weekly totals to 80+ miles on a plan whose longest run is 9.9mi, plus junk rows carrying 57,857-minute durations. Found because the AI Coach read those totals back as real training load and reported them as genuine mileage. Fixed by deleting the demo user's `SessionLog` rows in the seed script alongside the plans, rather than changing the FK to `Cascade` — cascade would be wrong for the app itself, where a logged session outliving the plan it belonged to is correct behavior.

**Both Mermaid diagrams live inline in `README.md` rather than as separate `.mmd` files or committed images.** GitHub renders Mermaid natively in Markdown, so a fenced block in the README is simultaneously "committed to the repo" and "rendered in the README" with no build step and no exported asset to drift out of sync with its source. Rendering verified on GitHub itself rather than assumed from valid-looking syntax.

**Diagram A shows the request path and the pure-package boundary in one picture, not two.** `plan-engine`/`strength-engine`/`scheduling` are drawn as a subgraph hanging off the procedure handler, so the one-way dependency graph and "these touch no DB and no network" are visible in the same frame as the Prisma/Postgres edge they deliberately avoid. The Anthropic edge is dashed and labelled allowed-to-fail for the same reason — the coach's isolation is an architectural claim, so it should be readable off the diagram rather than only in prose.

**The write-up was verified against the codebase before being committed, not trusted because it was detailed.** Three things changed as a result. The bundle-leak check was re-run (two checkpoints had touched `packages/contracts` since the last one): `PrismaClient`, `prisma`, `@anthropic-ai`, `anthropic`, `api.anthropic.com`, `@clerk/express`, `clerkMiddleware`, `CLERK_SECRET_KEY`, `getOrCreateUser` — zero occurrences, with the single `ANTHROPIC_API_KEY` hit confirmed to be the coach card's own "not configured" copy.
