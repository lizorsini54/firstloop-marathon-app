# Cadenza: Project Write-Up

## The problem

Most training apps handle one discipline. Cadenza was built for a more specific person: a first-time marathon runner who is also a seasoned lifter and an active cyclist, someone who needs a plan that coordinates disciplines rather than three separate trackers that happen to share a login. The starting brief asked for an authenticated app with the ability to record a training session, explicitly not a feature-complete product. What follows is an account of building considerably past that bar, and being deliberate about which parts of that extra scope were worth it.

## Architecture and the tradeoffs behind it

### Type safety from database to browser, verified rather than assumed

The frontend and backend share one contract: Zod schemas defined once, an oRPC router built on top of them, and the web app importing that router's *type* only, never its implementation. That last detail matters more than it sounds. Early on, the intake form needed a real value import of a validation schema, and the shortest path risked pulling in the router itself, which imports the database layer, which instantiates a live Prisma client at module scope. Whether a bundler would tree-shake that away isn't something worth gambling on when the question is "does server code end up in the browser." The fix was a dedicated export subpath that resolves straight to schema files and never touches the router, verified by grepping the built client bundle for Prisma and Clerk-backend strings. Zero matches. When the AI Coach was added later and pulled in the Anthropic SDK, the same check was re-run rather than assumed safe by analogy, for the same reason the first check existed: the risk is exactly this shape of dependency, so it gets re-verified every time that shape recurs. It was re-run once more while assembling this write-up, since two checkpoints had touched the contracts package since the last check — `PrismaClient`, `prisma`, `@anthropic-ai`, `anthropic`, `api.anthropic.com`, `@clerk/express`, `clerkMiddleware`, `CLERK_SECRET_KEY`, and `getOrCreateUser` all return zero occurrences in the built bundle. The single `ANTHROPIC_API_KEY` hit is the literal string inside the coach card's "not configured" message, not a value and not an import.

### A verification loop that actually catches things

Type checking, linting, and dead-code detection run locally and became a required CI check in the second checkpoint, before there was much code to check. Integration and end-to-end tests came later and were deliberately kept out of the fast local loop, since Testcontainers needs Docker and Playwright needs the whole stack running, but both are still required checks in CI. This loop caught real problems: a fresh CI install once let the Prisma client silently fall back to typed `any` because generation hadn't run yet — it failed in CI and passed locally, since the local `node_modules` already had a generated client sitting in it. More tellingly, a scheduling bug during peak-mileage weeks, where a specific combination of quality-run days left one strength session with no legal day to land on, wasn't caught by any unit test. Individually reasonable synthetic test scenarios don't surface interaction bugs; only eyeballing a full 39 weeks of real generated output did. That session had been silently dropped for six consecutive weeks before anyone looked.

### Deployment: real infrastructure, real bugs, one deliberate rollback

The app deploys to Railway as three independent services (Postgres, backend, frontend), and getting there surfaced a genuine chain of bugs worth naming because each one masked the next: a package manager resolving the wrong major version of a pinned dependency, database migrations that could only run at boot rather than at build time because Railway's build containers can't reach its internal network, and two separate failures traced back to the same root cause, Railway's dashboard displaying domains without their `https://` prefix, which silently breaks URL parsing and CORS when copied as-is.

Separately, a full three-tier environment split (dev, pre-prod, prod, with production changes only landing through a reviewed pull request) was built out completely, branch, CI trigger, branch protection, before discovering Railway requires a paid plan to run a second environment. That work was reverted rather than paid for. The reasoning: the cost wasn't justified purely to demonstrate a pattern on a take-home project. It's a plain, ordinary engineering tradeoff, and it's documented as one rather than quietly dropped.

### A swappable-program architecture, proven by reuse, not just claimed

The running plan generator and the strength scheduler are both pure, zero-dependency packages, and the strength program itself, currently a documented 12-week lifting cycle, is represented as data, not as logic. The scheduler that places sessions into a week was built generically from the start: "place a program's sessions around fixed days under its constraints," reading spacing and interference rules from the program's own data rather than hardcoding them.

That claim was tested almost immediately. A later requirement needed a "custom" strength mode with no named program at all, just a day count. Rather than build a second scheduler, one boolean in the original design turned out to be doing two jobs at once, avoiding the day before a hard run, and enforcing spacing between paired sessions, and Glute Gladiator happened to need both together for the same sessions, which is what let one flag get away with meaning two things. Splitting that into two independent properties made the custom mode trivial to support, and running itself later needed the exact same day-placement capability for its own frequency fix. Rather than duplicate the logic a third time, it was extracted into its own shared package that both domains depend on. The architecture held up under real, unplanned reuse, which is a better test than it holding up in the description of it.

### The AI Coach comments on training, it does not make training safe

Correctness and safety are the plan generator's and scheduler's job: progression, taper, peak-week intensity limits, session spacing, and injury-aware adaptation are all deterministic and unit-tested. The Coach is a single, isolated endpoint that reads a compact snapshot of recent training — adherence, missed sessions, and RPE over a 14-day detail window, plus four weeks of mileage trend for context — and says how it went. That separation is what allows the endpoint to fail without consequence: no API key is a first-class supported state, not an error, so a fresh clone or CI or a local environment with nothing configured runs the entire app with no failures. A live call that fails is caught and collapses to the same safe state. The model's system prompt explicitly tells it not to modify the plan, and there's nothing in the surrounding code that would let it if it tried.

### Honesty as a repeated design choice, not a one-off

This shows up enough times, in different parts of the system, that it reads as a real principle rather than a coincidence. The nutrition page states plainly that its guidance isn't personalized and that a real target needs information the app doesn't collect. When a knee injury is flagged, two strength movements with no documented safer alternative get dropped from the session rather than replaced with an invented substitute; the source program's own equipment swap table was read carefully first and found not to be injury-oriented at all before any of this was built. Weekly mileage is labeled as what it actually measures: the dashboard's planned-vs-logged chart says "long-run distance" because long runs are the only sessions prescribed by distance, and a week whose runs were all logged by duration reads as "not measured in miles" rather than as a zero.

The day-economy check earned the same treatment, by overruling me. It was added to catch weeks where the schedule can't fit what it promised, and it fired on the app's own default configuration. The plan for the final checkpoint assumed that was a matter of nudging the running and bike day counts. Actually sweeping the configuration space through the check itself, rather than picking numbers that sounded reasonable, showed that assumption was wrong: the strength program needs four free days a week, every running or bike day consumes one, and the only configuration that keeps the full program is three running days and no bike at all. So the defaults split — the seeded demo gives up its bike day to keep the real program on screen, and a new user's first plan defaults to a lighter custom program that leaves an actual rest day. Both were then verified clean by generating real plans and running the check against them, and a plan built specifically to trip the warning is part of the walkthrough. What did not happen is the thing that would have been easiest: the check was never thresholded, softened, or taught to stay quiet. The warning was always telling the truth — four sessions really did not fit in two days — and the fix was to stop asking the app to do something that doesn't fit, not to stop it from saying so.

### Real bugs found by using the system, not just testing it

Several of the most important fixes in this project came from generating real output and looking at it, not from code review in the abstract: the six-week silent session drop mentioned above, the day-economy conflict that only appeared once a full plan was browsed end to end, and 450 orphaned session logs, including junk rows carrying 57,857-minute durations, discovered because the AI Coach reported 80-plus-mile weeks on a plan whose longest run is 9.9 miles and that report was taken seriously enough to trace back to its source rather than dismissed as a model quirk. The cause was a foreign key set to null rather than cascade on delete, so every past reseed had left a full training history behind and stacked another one on top.

## What's explicitly out of scope, and why

Mobile responsiveness, social features, and wearable integrations were never attempted, they're genuinely separate projects. Editing or rescheduling a planned session, and selecting among multiple training plans, are both real gaps, tracked rather than silently absent.

One limitation is worth naming precisely, because labeling it honestly is not the same as solving it. The plan prescribes easy and quality runs by duration, not distance, so it has no planned distance for them — only long runs carry one. The app now says so everywhere that number appears rather than implying total volume, and the demo's logged history derives a distance from each run's duration and pace, which is legitimate for a record of something that happened. But the planned side still has no honest distance to state, and inventing one would be exactly the kind of fabrication the rest of this document is about avoiding. Doing it properly means asking the runner for a typical pace once and applying it transparently, which is future work, not a label change.

A handful of further items were found during a coach-and-designer persona review and consciously deferred rather than fixed under time pressure: no periodic cutback or step-back week during base and build phases, a peak long-run distance that's a fixed constant rather than scaled to a runner's experience or current mileage, strength prescriptions that step only when a training block changes rather than adjusting week to week, no explanatory text on the custom strength mode, and interference and spacing rules that work correctly but are invisible in the UI, so a user has no way to tell a deliberate scheduling choice from a coincidence. Recommending a new strength program automatically, based on a user's evolving goals, was named early as a real future direction and deliberately not attempted now, the program stays exactly as documented rather than being partially parameterized.

## How agents were used to build this

The build ran as a sequence of checkpoints, each one planned before any code was written, reviewed after, and never self-continued into the next without an explicit go-ahead. Every real architectural or scope decision was logged as it was made, not reconstructed afterward, which is what makes an accurate account like this one possible at all.

The most valuable technique wasn't the code generation itself, it was treating the system as something to be evaluated from outside its own logic, not just tested against its own assumptions. A dedicated pass asked for two honest personas, an experienced running and strength coach, and an experienced app designer, to generate real plans and actually use the product, not read the code and reason abstractly about it. That review is where the peak-week intensity collision, the day-economy conflicts, and the injury-flag gaps were actually found, problems that every individual piece of the system had already passed its own tests for, because the failure only existed in how correctly-built pieces interacted with each other.

## What's next

An adaptive version of the strength program's pull-up progression, currently reference content only. Recommending a new strength program automatically as a runner's goals change. True week-to-week progression within a strength block rather than a step at block boundaries. A cutback week in the running plan's base and build phases, and a peak long-run distance that scales with experience and current mileage rather than staying fixed. Deriving a planned distance for duration-only runs without fabricating one, most plausibly by asking for a typical pace once and applying it transparently rather than guessing silently. Making the scheduler's interference and spacing decisions visible in the UI, not just correct underneath it. Editing and rescheduling a planned session. A tool-using version of the AI Coach that can query specific data rather than receiving a fixed window. An agentic code-review step in CI. Deployment to a hyperscaler via Terraform, which was named as valuable bonus work from the start and intentionally left for after this submission.
